# M3 Knowledge Layer Verification Report

**Date:** 3 November 2026 (Africa/Nairobi)  
**Status:** Implementation complete; acceptance review pending. This report covers the owner-authorized M3 knowledge-layer scope. The approved PDF labels deterministic rules as M3; this work records that scope sequencing decision in D-020 and does not claim the rule engine is implemented.

## Existing implementation inventory and plan

Before changes, M2 already provided PostgreSQL tables for networks, blocks, transactions, receipts, logs, checkpoints, entities, rule-shaped observations and observation evidence. It already enforced network-scoped source foreign keys and atomic block/checkpoint writes. Entities had no address validation or provenance timestamps. Observations did not represent direct chain participation, and there was no relationship table, knowledge ingestion service or retrieval service. M2 reorg rollback refused to remove evidence-referenced blocks. See [M2 verification](M2_VERIFICATION_REPORT.md).

Implementation extended those existing records instead of replacing them: validate/normalize addresses; add direct observations and relationship/evidence tables; provide a separate bounded idempotent service; retract derived records before observer rollback; add network-scoped retrieval; verify using real PostgreSQL and the persisted Whitechain sample.

## Knowledge model and database changes

- Migration 003 adds original address and entity timestamps, direct observation source fields, optional related entity, and `relationships` / `relationship_evidence`. All entity, relationship and source references are network-scoped with composite foreign keys.
- Migration 004 deduplicates nullable transaction evidence and adds a unique source identity. Migration 005 removes duplicate relation-to-transaction evidence links left by early replay verification.
- EVM addresses must be `0x` plus 40 hex digits. Canonical keys are lowercase; the first observed spelling is retained. Entity types are `wallet`, `contract`, `token`, `unknown`. Since sender/recipient alone cannot prove wallet status, participants start `unknown`. Addresses that emit persisted receipt logs are classified as contracts. No identity labels or ownership are inferred.
- Observations generated by enrichment include network, subject, optional related entity, kind, block number/hash, transaction hash, optional log index, source timestamp and structured attributes. They are flagged as derived and uniquely keyed to their source fact.
- Relationships distinguish `observed`, `aggregated` and `inferred`. Current enrichment creates aggregated `transacted_with` and `interacted_with_contract` relationships. Evidence is linked through `relationship_evidence` to the observation evidence record; evidence references block, transaction and optional log, with foreign keys preventing cross-network sources. No confidence score is introduced.
- The processing service is independent of the indexer. It reads canonical persisted transactions and logs in a bounded batch and commits entity, observation, relationship and evidence changes in a PostgreSQL transaction. Duplicate retries preserve counts and source identities.
- Observer rollback removes only derived knowledge supported by the affected block suffix before deleting the source records. Non-derived observations retain restrictive evidence protection. Replayed blocks can be enriched again. Derived-only entities with no remaining knowledge references are removed; shared entities remain.
- `KnowledgeService` provides entity lookup, paginated observations with block-range filters, related entity/relationship lookup, pairwise relationship retrieval, relationship evidence, and transaction history with receipt data.

## Live Whitechain knowledge demonstration

The workflow used the existing persisted Whitechain Sepolia data (chain ID 1874), not fixtures: blocks 12,057,643–12,057,645, four transactions, four receipts and two logs. `KnowledgeService.ingest(1874)` processed four transactions; a second invocation processed the same four and left generated fact/evidence counts unchanged. The resulting database contained four entities, nine observations, three aggregated relationships and nine evidence references.

Example queried relationship: `0xbb4d7fb1c2950740b3b2bcd6fd467b26e294c783` interacted with contract `0x0ac538e15e4c7a27e6e38025bed911b8975044f0` at block 12,057,644. Its relationship evidence resolves to block hash `0x7e2d355059b3541e9220e9208a5f5c60a1f77f5583051e359a45a36a9eecc7b8`, transaction `0x77e620bffe99cefd4d2b8d71009b584f588186375846fe9f7dcb24b342b5b4dd`, log index 0. The same transaction receipt is stored under that transaction hash. The query returned the relationship and source references from PostgreSQL.

## Query plan and limitations

On the four-transaction local dataset, `EXPLAIN (ANALYZE, BUFFERS)` for an entity observation page used `observations_entity_block_idx`, read three shared buffers and reported 0.024 ms execution time (planning 0.126 ms). This is a tiny local query-plan check, not a representative throughput benchmark or latency promise.

The current decoder records transaction participation and raw log emission only. It does not decode token transfers or arbitrary event schemas, distinguish EOAs from contracts except for observed log emitters, or infer ownership/identity/intent. The service is callable internally but has no CLI/API endpoint. Knowledge enrichment is a separate call and must be run again after observer replay. Migrations are forward-applied; 004/005 are data cleanup steps and should not be reversed without restoring a pre-migration backup.

## Acceptance evidence

Schema and indexes are applied; addresses are network-scoped and normalized; direct knowledge is derived from actual persisted indexed records; relationships have retrievable source evidence; duplicate processing is safe; rollback/replay invalidation is covered by PostgreSQL integration tests; the live demonstration and representative indexed query plan succeeded. The complete project test suite reported 19 passing tests, zero failures and zero skips. Dashboard, API, deterministic detection rules and production-scale performance remain outside this authorized knowledge-layer milestone.
