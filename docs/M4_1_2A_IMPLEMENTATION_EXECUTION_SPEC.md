# ORBIS M4.1.2A — Implementation Execution Specification

**Status:** implementation preflight; no application or migration changes are authorized by this document.
**Baseline:** [Network Identity and Selection Plan](M4_1_2A_NETWORK_IDENTITY_PLAN.md) and [Deployment Readiness Closure](M4_1_2A_DEPLOYMENT_READINESS_CLOSURE.md). Their approved policies are binding.
**Scope:** turn those policies into ordered, reviewable engineering work. M4.1.2C remains downstream. This is not production approval.

## 1. Readiness finding

Implementation can begin in an isolated development environment for identity primitives, context propagation, profile parsing, runtime selector conversion, and test harness preparation. PostgreSQL schema/function/grant work requires an actual PostgreSQL instance and approved role/audit decisions before it can be accepted. The present application does not demonstrate runtime/migrator principal separation: it creates one direct `psycopg` connection from one DSN, and the CLI invokes `migrate()` on the runtime store. Therefore separate roles must not be described as already supported; the connection lifecycle and deployment entry point must be changed as part of the implementation.

No production readiness is declared. Constraint removal, historical backfill, write enablement and deployment remain blocked until the closure document's owner assignments, audit custody/retention, evidence approval, maintenance rehearsal and recovery gates are closed. No historical association is inferred. Existing unresolved registry rows and dependent records must be preserved and kept runtime-ineligible. SQLite remains single-network only. A and B are released together; no old chain-ID-only writer may write after the compatibility boundary.

## 2. Existing architecture findings

### Network registration and selectors

- `Settings` in `src/orbis/config.py` loads one `ORBIS_RPC_URL`, one explicit `ORBIS_CHAIN_ID`, one database URL and descriptive network metadata. It has no profile collection, selected profile, genesis identity or precedence rules. It validates required strings and parses chain ID, but does not reject booleans at typed APIs (configuration is string based) or enforce a positive chain ID.
- `RpcClient` in `src/orbis/chain/rpc.py` exposes `eth_chainId`, head, blocks, receipts and logs. It has no block-zero identity verifier. `Indexer.verify_network()` checks chain ID and reads head only.
- `PostgresStore._network_id()` in `src/orbis/observer/postgres.py` upserts on `chain_id`; `migrations/001_initial.sql` has `networks.chain_id UNIQUE`. This is the network registration path and it can be reached from `commit_block()` without RPC verification.
- `PostgresStore.checkpoint`, `block_hash`, `rollback_from` and `count` select by chain ID. `KnowledgeService._network()` in `src/orbis/knowledge.py` also selects by chain ID; public knowledge APIs and nested calls propagate chain ID and may re-resolve it repeatedly.
- The indexer protocol and implementation pass chain ID to checkpoint, common-ancestor, commit and rollback operations. Those parameters must become a verified/resolved context contract.
- Most tables already use `network_id` as FK and composite key scope. `EvaluationRepository` operates internally by `network_id`, but validates the evidence envelope's `network_chain_id`; `evaluation_identity()` in `src/orbis/rules/identity.py` implements `orbis-evaluation-v1` using chain ID only. This is an M4.1.2 integration edge: preserve historical v1 behavior and add fingerprint-bearing v2 paths without making M4.1.2C part of this work.
- `SqliteStore` in `src/orbis/observer/store.py` keys blocks, transactions, logs and checkpoints by chain ID. It has no registry or fingerprint support. Preserve it for one selected network and reject multi-profile SQLite configuration.

### Database, migration and startup mechanisms

- Migration files are ordered SQL scripts in `migrations/001_initial.sql` through `012_m4_lifecycle_hardening.sql`. Existing PostgreSQL trigger functions protect evaluation/rule immutability, append-only evidence/audit structures and integrity invariants; these are precedents, not network-identity controls.
- `PostgresStore.migrate()` creates `schema_migrations`, loops through SQL files in a transaction, and runs at startup from `src/orbis/cli.py`. `src/orbis/db_migrate.py` is a separate command but uses the same `ORBIS_DATABASE_URL` and `PostgresStore` class. No schema compatibility handshake, migration checksum, or separate principal is enforced.
- `PostgresStore` opens one `psycopg.connect()` directly; no pool abstraction or role-specific connection factory exists. The optional schema path uses `SET search_path`; any future privileged function must not trust caller-controlled search path.
- Per-block ingest is transactional. Knowledge enrichment uses transaction blocks; reorg cleanup and M4 invalidation are in one database transaction. Migration scripts run transactionally under current implementation, subject to PostgreSQL's per-command transactional support.

### Tests, audit and deployment evidence

- `tests/test_postgres_integration.py` is real-PostgreSQL integration infrastructure gated by `ORBIS_TEST_DATABASE_URL`; it creates a unique schema, applies actual migrations and drops that schema at teardown. It tests FKs, triggers, concurrent evaluation persistence and network scoping. Its fixtures call `_network_id(chain_id)`, commit by chain ID and query `networks` by chain ID; these assumptions must be migrated. Tests skip when no PostgreSQL test URL exists.
- `tests/test_observer.py`, `tests/test_rpc.py`, `tests/test_rules.py` provide unit/fake-RPC coverage. `tests/test_rules.py` already characterizes the v1 same-chain collision and v2 fingerprint distinction. These do not replace PostgreSQL tests for constraints, locks, grants, triggers or `SECURITY DEFINER` behavior.
- Current audit protections concern M4 evaluation lifecycle, not network identity changes or rejected network operations. No identity audit ledger, external append-only sink, identity retention rule, role matrix, or network repair function is implemented/verified in this repository.
- `README.md` contains local operation/backup instructions; repository evidence does not demonstrate production backup restoration, writer fencing, or an operational compatibility matrix.

## 5. Database objects and permission design

Proposed schema (names finalized in migration review):

- `networks.genesis_hash`, `fingerprint_scheme`, `network_fingerprint`, nullable together for unresolved legacy rows. Checks enforce all-null or valid all-present tuple and canonical syntax. Unique tuple on `(chain_id, fingerprint_scheme, network_fingerprint)`; preserve the original `network_id` PK and all dependent FK/key structures. Drop chain-ID uniqueness only in the coordinated boundary migration.
- `network_identity_audit` append-only ledger: event ID, timestamp, event type/outcome, network ID (nullable for failed new registration), chain ID, scheme/fingerprint where known, stable profile ID, database change ID, actor claim, `session_user`, `current_user`, evidence packet reference/digest and structured non-secret details. DB grants deny UPDATE/DELETE to service/admin roles; external custody/export and retention are separately governed.
- Optional `network_identity_authorizations`/nonce table if database-enforced one-use grants are chosen. Authorization binds action, network ID, expected old tuple/state, proposed tuple, evidence digest, change ID, expiry and unique nonce; consume atomically. A caller-supplied reason alone is not authorization.
- Trigger preventing identity tuple mutation once set, including ordinary metadata upsert paths. A controlled repair function can perform an approved exact transition only after validating a one-use authorization and uniqueness. The trigger must recognize authorization through transaction-bound state/table row, not a forgeable custom GUC alone.
- Backfill/repair functions should be narrow (`resolve_unresolved_network` and, only if necessary, `repair_network_identity`), return an explicit outcome, lock the row, validate exact arguments, and append ledger entry in the same transaction.

### Privileged PostgreSQL functions

Prefer `SECURITY INVOKER`; if `SECURITY DEFINER` is required to keep table update rights away from the caller, the function owner must be a dedicated `NOLOGIN` least-privilege owner, not superuser/table owner or application role. Revoke default `PUBLIC` execute and grant only to a dedicated administrative login/group. Set a fixed safe `search_path` in the function definition (trusted schema first, then `pg_catalog`; exclude writable schemas and `public` unless locked down), schema-qualify objects, avoid dynamic SQL, and audit function definition/owner/grants. Validate positive chain/network IDs, exact hash/digest formats, supported scheme, text/JSON size limits, expected old state, action enum, expiry, nonce, evidence reference and duplicate tuple. Limit lock scope to one target row and use deterministic lock ordering for any more than one row. Use `session_user` to identify the authenticated login; `current_user` inside a definer function is the function owner. Record both, and never treat `current_user` alone as the initiating actor. A claimed operator ID must map to separately authorized approval evidence. Transaction ID and request/change ID provide replay/audit correlation.

### Roles and pools: actual support assessment

Today there is one DSN, one direct connection and no pool or role routing. Separate principals are therefore not an existing capability. Implement explicit configuration/connection factories for runtime and migration, with runtime processes receiving only a runtime credential and migration job only a migrator credential. A pool is not inherently required; separate direct connections per process/principal suffice. If pooling is introduced, pools must be independently constructed from distinct DSNs and never switch roles via caller-provided `SET ROLE`. Suggested roles are `orbis_runtime` (DML only on operational data and execute only approved runtime functions), `orbis_migrator` (DDL and migration ledger, used only by deployment job), and `orbis_identity_admin` (execute narrow backfill/repair functions, no unrestricted table update); owners are `NOLOGIN`. Exact grants and ownership require DB/security owner approval and PostgreSQL proof. Current runtime's `migrate()` method must be removed from normal application startup or made unreachable to runtime credentials.

## 6. Security model and audit failure behavior

1. Trust is layered: unverified configuration permits no DB network operation; verified context permits exact registry resolution only; resolved context permits scoped runtime operations. Only RPC verifier and exact database resolver factories may create trusted states.
2. Profile name is local selection metadata only. Chain ID is not identity. Fingerprint is locally derived, scheme-versioned and immutable. `network_id` is a local scope key, not proof of network identity.
3. Runtime cannot update identity columns, backfill, repair, run DDL, or resolve by chain ID. Identity mutation paths require specific authorization and a durable audit record.
4. For an identity mutation, ledger append and row update commit atomically. If the database audit ledger cannot be written, mutation fails. Export to external append-only custody may use a transactional outbox; rollout cannot enable privileged operations until export is healthy, backlog limits/alerts are defined, and owners accept the custody boundary. For rejected privileged operations, persist a denial event in a separate transaction that cannot be rolled back with the failed operation; if even that durable record is unavailable, fail closed, emit an out-of-band operational alert and do not retry the privileged action. This design must be proven under PostgreSQL failures.
5. Successful registration and runtime verification should have defined event volume. Avoid logging each routine read unless approved; do record identity creation and any mismatch/denial. A mismatch must not mutate registry. Use stable IDs and evidence digests; never record DSN, credentials, raw endpoint URL or secrets.
6. Retention, legal hold, deletion policy, ledger reader access and external sink are owner decisions still open. Retain at least as long as registry/dependent data plus approved incident/audit period; numeric duration is not yet set.

## 7. Historical backfill and repair contract

Backfill is per existing `network_id`, never a row recreation or child data movement. Required evidence packet and Class A/B standard are specified in the closure document; this spec makes them execution inputs. Read-only inventory is captured first. The operator chooses the explicit endpoint profile; live RPC verifies configured/stored chain ID and block zero, while historical evidence binds that profile and database/environment/row to the records. Current RPC alone, names, provider, chain ID, latest block, present unversioned config or operator memory are insufficient. Mixed-network or contradictory history is quarantined.

Two authorized reviewers approve Class B evidence; Class A receives the required independent verification and review. Packet includes identity observation and locally calculated fingerprint, provenance references, evidence class/rationale, existing row expectation, database/environment ID, change ID, operator, reviewers and timestamps. The protected function rechecks all database-verifiable invariants under row lock and consumes one-use authorization. External evidence authenticity/reviewer identity must be verified by the administrative workflow and referenced by immutable digest; a DB function cannot prove the real-world truth of arbitrary text supplied by a caller.

One row is one transaction. Exact tuple retry returns already-applied and emits a retry audit event; different tuple, stale expected state, uniqueness conflict, missing authorization, missing evidence or audit sink outage is a hard failure and quarantine. Batch interruption does not undo committed rows. Resume from a fresh inventory; do not rerun blindly. Repair follows the same control pattern with stronger change approval and explicit expected prior tuple. No repair can automatically merge/split records or assert historical identity without new evidence.

## 8. Runtime/schema compatibility and rollout boundary

The matrix is a required release artifact; exact version strings/checksums are assigned by release owner.

| Runtime | Schema | Allowed behavior |
|---|---|---|
| Current legacy runtime | Current schema with `UNIQUE(chain_id)` | Existing single-network operation only, before boundary; no identity claims |
| A+B identity-aware runtime, writes gated | Current schema before migration | Diagnostic/verification only if explicitly implemented; no writes or chain-only selector fallback |
| A+B identity-aware runtime | New identity schema, unresolved rows present | Exact registry operations; unresolved rows excluded from all runtime data selectors; writes only for verified/resolved contexts |
| Legacy runtime | New schema after chain-ID constraint removal | **Rejected before writer startup**; no read/write compatibility exception for network-dependent code |
| Partial migration / unknown version / drift | Any runtime | **Rejected; all network writers remain gated** |
| New runtime | Older or newer unsupported schema | **Rejected before writes** |

Remove runtime auto-migration. A separate deployment migration job applies a reviewed immutable migration with migrator credential. Record migration version/checksum and an explicit schema capability/version. At startup, before opening any writer path, identity-aware runtime checks compatibility and confirms required objects. Partial state, checksum mismatch, unsupported version or old binary after boundary must fail closed. Migration is forward-only. Before the boundary, restore old schema/code only if no same-ID registrations/backfill/new writes occurred and the restored state is verified. After new identity writes resume, use compatible forward fixes; any backup restore must explicitly account for loss/reconciliation of post-backup writes. Never restore a chain-only writer after dropping its conflict target.

| Evaluation compatibility | Historical v1 records plus v2 same-chain contexts | v1 keys/readers unchanged; v2 includes scheme/fingerprint and separates networks; envelope tuple verified | Unit + PostgreSQL |

## 10. Staging execution strategy and verification gates

1. Build an empty disposable PostgreSQL database and a populated clone from a sanitized fixture/backup. Capture IDs, row counts, key/FK invariants and schema version before change.
2. Apply migrations only through migration entry point and distinct migrator principal. Verify migration checksum and catalog state. Run old/new compatibility matrix while all writes are gated.
3. Create runtime, migration, identity-admin and read-only principals with proposed grants. Prove runtime cannot DDL, mutate identity, call repair/backfill, or access migrator credentials. Prove `session_user` and `current_user` audit values in function calls.
4. Run full PostgreSQL acceptance suite including same-ID concurrency, constraint/trigger behavior, function/search-path security, role denials, transaction interruption, audit failures and cross-network rollback. Run unit/RPC/config/SQLite suites separately.
5. Exercise real A+B processes concurrently against staged PostgreSQL using explicit profiles and different endpoints for one identity; inspect independent checkpoints and no chain-only selectors. Exercise wrong endpoint and unresolved row rejection.
6. Stage only evidence-approved backfill examples. Test Class A, Class B dual approval, C/D quarantine, duplicate conflict and partial restart. No production historical data is used to invent expected associations.
7. Test audit external export, append-only custody, retention configuration and failure alerting with owners. Restore a backup into a separate target and verify it before permitting any maintenance-window proposal.
8. Produce a release artifact: code/schema compatibility matrix, migration checksums, catalog/grant reports, test output, preservation manifest, audit export receipt, backfill evidence/skip/quarantine ledger, restore results, operator/reviewer approvals and exceptions.

Gates: **G1** interface/profile contract approved; **G2** primitives and unit tests pass; **G3** actual PostgreSQL schema/security tests pass; **G4** compatibility and populated-upgrade preservation pass; **G5** staging multi-process and recovery rehearsal pass; **G6** owners close closure blockers. Production migration/write enablement additionally requires a separately approved maintenance window and is outside this specification.

## 11. Outstanding owner decisions

These do not reopen settled architecture policy.

- **Application owner:** final profile JSON schema/maximum size and exact precedence/error rule when legacy singular variables and profile collection coexist; schema capability/version compatibility convention.
- **DB/security owner:** actual role names, ownership, grants, migrator credential delivery, whether a `SECURITY DEFINER` function is required, one-use authorization mechanism, PostgreSQL version support and grant proof.
- **Data/service + security/compliance owners:** identity audit sink and independent custody, numeric retention and legal hold/deletion policy, read access, export lag threshold, denial-event fallback/alert route.
- **Network operations/data owner:** Class A/B evidence workflow, reviewer identities/authority, external provenance verification, quarantine and recovery decision process.
- **Release owner + DB operator:** supported runtime/schema matrix identifiers, writer fencing, maintenance window, RPO/RTO, backup/restore rehearsal acceptance and forward recovery ownership.
- **M4.1.2 owner:** coordinate v2 envelope/evaluation changes and retain v1 compatibility; no M4.1.2C evaluation-rule scope is authorized by this preflight.

## 12. Milestones and implementation gates

1. Interface/security review: approve profile precedence, context API, matrix template, audit and admin-function design. No migrations.
2. Identity and config foundation: fingerprint vectors, trust-state factory, profile parser and SQLite rejection. Gate G2.
3. Runtime propagation: observer and knowledge APIs move to context; remove chain-only selectors; rule envelope coordination. Keep writes gated.
4. Database and principal boundary: reviewed additive migration, role separation, immutable registry and audit controls; actual PG unit-of-work/security testing. Gate G3.
5. Backfill/admin workflows and compatibility: evidence packet, authorization, idempotency, unresolved quarantine, startup rejection matrix. Gate G4.
6. Integration/staging: A+B together, populated migration, concurrency, audit sink, restore and writer-fencing rehearsal. Gate G5/G6.
7. Production proposal: separate deployment approval only after all closure blockers and evidence are complete. This document does not authorize that step.

## 13. Final implementation decision

Engineering may begin isolated development on pure identity/context/config and API propagation. Begin no schema deployment or historical association work until actual PostgreSQL controls and owner decisions are available. Real PostgreSQL is mandatory for every constraint, locking, trigger, grant, role and function-security claim. Runtime/schema compatibility, old-writer fencing, unresolved-row ineligibility, coordinated A+B release, SQLite rejection and durable audit controls remain release/deployment blockers until demonstrated. This is an implementation specification, not a production readiness declaration.
